# 本地存储、迁移与 Supabase 同步

网页继续由 GitHub Pages 托管，默认使用本地 IndexedDB。“云端同步”登录后可选择迁移本地库或使用该账号已有的云端库。代码仓库不包含论文内容；原本地库保留，云端缓存按项目和账号分别存储。

## 首次配置与迁移

1. 在 Supabase 的 SQL Editor 依次运行 `001_supabase.sql` 和 `002_cloud_sync.sql`，每个脚本执行一次。已经执行过 001 时只执行 002，不部署测试中的 auth 替身。
2. 在 Authentication → Users 创建邮箱登录账号。个人项目可关闭允许新用户注册的开关；网页只提供登录入口。
3. `docs/cloud-config.js` 配置项目根 URL（不带 `/rest/v1/`）与 publishable key。密码、JWT、secret key、service_role 不能写入源码或提交 GitHub。
4. 在保存旧库的原浏览器、原 GitHub Pages 地址打开网页，先“导出库”备份。点击“云端同步”登录，核对本地与云端数量。
5. 点击“迁移本地库并启用同步”；云端已有数据时可“合并本地库并启用同步”，或仅“使用云端库”。导入沿用现有匹配规则，保留星标，原本地库不会删除。
6. 等到顶部显示“已同步”。新设备打开同一网页、登录同一账号，首次选择“使用云端库”，核对论文、星标、引用脉络和全局排行。

文件夹监听按账号分别记住。首次启用云端时重新选择目标文件夹，之后在权限允许时恢复。网页保持打开才会读取 skill 的新输出并同步；关闭网页时 skill 仍只生成本地文件。单篇总结格式无需改变。

## 同步与恢复

- 编辑先原子写入本机论文/设置与待同步队列，再更新界面；刷新、断网、退出登录不会清除该账号的队列。后台每 30 秒核对一次，恢复网络时重试，也可“立即同步”。
- RPC 在一笔数据库事务中检查修订号、更新关系表、记录删除与操作编号。后续上传关系表差量；星标只发送文献 ID 和布尔值，不重传总结/引用，也不重建引用索引。
- 请求成功但响应丢失时，操作编号保证重试不会重复写入。服务器只存编号、摘要和修订号，每 100 次提交清理早于最近 1000 个版本的操作记录；超过窗口的旧重试会安全地转为冲突。删除标记保留以通知离线设备。
- 新设备首次分批缓存全部论文以保持全文搜索、详情与离线功能。变更目录每页最多 100 条，详情每批最多 50 篇；随后只下载有变化的论文和设置，未变化时只查状态。
- 已同步且无搜索词时，全局排行读取 SQL 的 `COUNT(DISTINCT source_id)`，按页取回；同数值按数据库排序。搜索沿用原有 Unicode/标点归一化规则，离线或待同步时使用本机分析缓存。
- 多设备编辑发生版本冲突时停止上传并保留本机队列，不自动覆盖或合并完整版本。可导出本机备份，采用云端版本后再导入需要的内容；也可明确选择用本机完整库替换云端。处理前下载本机备份，替换云端前还会下载云端备份。
- 清空云端库和删除论文会同步到其他设备，磁盘原文件保留。Table Editor 中的手动改表不会产生协议需要的修订号/变更记录，日常编辑应通过网页完成。
- 退出后显示原本地库；请求固定使用缓存所属账号的令牌，防止其他标签页切换账号时串库。浏览器存储被清理会丢失尚未上传的操作，仍需保留独立备份。

匿名用户无权读表或调用同步/统计 RPC。所有公开表均启用 RLS，按 `auth.uid()` 隔离；RPC 不接受替代当前身份的 owner 参数。

## 已完成的本地升级

- 主存储改为 IndexedDB：每篇论文一条记录，设置与修订号单独保存；星标只写对应论文。事务完成后才更新界面，失败保留上次状态并显示持续提示。
- 首次打开读取旧 `summarize-paper-library-v2`，其次 v1，并原样保留旧键作为升级前副本；只在新数据库未初始化时读取旧数据，空库也不会反复“复活”旧记录。原始文件与旧存储不会删除。
- 不支持 IndexedDB 的环境使用紧凑 JSON 兼容存储；此模式仍需整库写入，有浏览器容量限制。IndexedDB 打开失败时停止写入，不另建一个空库遮住已有数据。
- 多标签页通过 BroadcastChannel 通知，写入检查库修订号；过期写入被拒绝并刷新，避免覆盖另一标签页的修改。兼容存储尽可能使用 Web Locks；不支持 Web Locks 时不保证跨标签页竞争写入，建议只开一个页面。
- 新论文和引用记录使用持久编号；旧论文编号保留。元数据更新会匹配原记录编号。无法可靠判断对应关系时保留独立条目，并报告无法应用的历史合并，不猜测。
- 文献搜索缓存论文级引用文本；分析缓存随数据/设置版本失效，星标与页面导航不重算引用。点击排名只更新选择详情；合并候选在展开时创建。
- 文件夹仍每 5 秒扫描文件信息，只有首选总结或同组 Markdown 变化才读取和解析该组。成功保存后才记录缓存；解析失败会重试。删除磁盘文件不会自动删除库内论文，保持原有行为。

## 使用与恢复

1. 在原来使用的浏览器、原网页地址打开新版页面，旧库自动升级。其他浏览器或不同网址无法访问原浏览器存储。
2. “导出库”生成 `format: summarize-paper-library`、`schema_version: 3` 的完整备份，包括星标、引用原文和分析设置。单篇 skill 输出仍使用自己的 schema 版本，两者互不替代。
3. “导出迁移包”生成关系表格式，保留所有原始总结和引用语境，不重复附带一份整库 JSON。导出会核对记录编号、外键、文献归属、方向和不同来源论文计数。
4. 两种导出都能通过文件导入或粘贴 JSON 恢复。导入沿用合并方式，不会清除库中其他论文。需要在空库做完整恢复时，先单独备份现库，再明确执行清空和导入。
5. 保留库备份、迁移包和原始 skill 文件直到云端核对通过。浏览器存储仍可能被清理，升级前副本仅供本机恢复，不能代替独立备份。

## 离线迁移演练

使用网页新版导出的完整库或迁移包：

```bash
node scripts/prepare-migration.cjs /path/to/library.json /path/to/new-migration.json
node scripts/prepare-migration.cjs /path/to/new-migration.json
```

命令只读取本地文件、校验数据并按需写出新文件，不联网，不覆盖现有输出。不含稳定引用编号的旧备份，应先导入新版网页再导出。论文内容、迁移包和数据库密钥不要提交到代码仓库。

迁移包的六张表：

| 表名 | 内容 |
|---|---|
| `papers` | 持久论文 ID、排序和总结内容；引用分组单独存储 |
| `sources` | 统计意义上的去重来源论文 |
| `source_members` | 原始论文记录到去重来源的映射 |
| `works` | 去重后的被引文献及成员编号 |
| `reference_groups` | 每篇论文原始方向名称、说明和顺序 |
| `citation_records` | 每条原始引用、稳定记录 ID、出处、关系与分类依据；关联来源与被引文献 |

`analysis_settings` 包含方向映射、可撤销的合并规则和历史标识映射；它在云端放入 `paper_library_state`。一个来源对同一文献的多个编号或方向仍分别保留，统计使用 `COUNT(DISTINCT source_id)`。

## 验证

```bash
npm ci
npm run check
npm test
python -m unittest discover -s tests -v
```

Node 测试使用 fake-indexeddb 验证 IndexedDB 事务，使用 PGlite 执行 PostgreSQL SQL，覆盖外键、不同来源论文统计、分页、账号隔离、同步 RPC、断网与刷新恢复、响应丢失重试、删除标记、版本冲突和主应用集成。UI 使用程序化元素替身；这些不是实际浏览器视觉测试，也不替代真实账号登录与首次上传核验。

数据库权限设计参考 [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)。本地 PostgreSQL 验证使用 [PGlite](https://pglite.dev/docs/)。
